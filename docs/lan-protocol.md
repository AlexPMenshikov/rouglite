# LAN-протокол

Сервер отдаёт клиент по HTTP и держит WebSocket на `/ws`. Сообщения — JSON с полем `type`. В кооперативе сервер авторитетен: он выполняет валидированные действия на общем забеге и рассылает снимок комнате. Устройство движка — в [`architecture.md`](architecture.md).

Авторитет живёт в процессе сервера и не зависит от окон браузера.

## Клиент → сервер

| Type | Fields | Кто и что |
|---|---|---|
| `list` | — | Любой; отвечает списком комнат и, пока сокет не в комнате, подписывает его на обновления списка. |
| `runs` | — | Любой; спрашивает забеги, сохранённые на диске сервера. Ответ — `runs`. Браузерный клиент этот запрос не шлёт: в меню он показывает список комнат. |
| `create` | `name`, опц. `classId`, опц. `luck` | Новый; создаёт комнату и игрока-хоста. `luck` — удача мета-прогрессии хоста, влияет на находки золота партии. |
| `join` | `room`, `name`, опц. `classId` | Новый; входит новым героем. Продолжить героя можно только через `reconnect` с его токеном. |
| `reconnect` | `room`, `token`, `name` | Новый; возобновляет игрока по сохранённому токену. Токен — единственное удостоверение для возврата в сессию. |
| `selectClass` | `classId` | Любой игрок; класс запоминается до старта забега. После старта сменить нельзя — герой уже создан. |
| `start` | `options` (опц. `classId`) | Только хост; начинает забег всей партии на картах 64×64. Неизвестный `classId` заменяется классом хоста; остальные поля не используются. Стиль берётся из свойства локации. |
| `kick` | `playerId` | Только хост; выгоняет **отключённого** игрока и освобождает слот. Подключённого так не выкинуть — он вернулся бы переподключением. |
| `action` | `action`, `args` | Имя — в allowlist сервера и проходит проверку аргументов, соединение — в лимите (20/с). Выполняется на общем забеге. |
| `chat` | `text` | Любой игрок; лимит 5 сообщений за 5 с. |

`classId` — один из `PLAYER_CLASSES` (`js/config.js`), иначе `paladin`. Старое имя `tank` не в списке, поэтому падает в `paladin` общим правилом неизвестного `classId`. Вместимость комнаты — `CONFIG.MAX_PLAYERS`. Комнаты живут в памяти, максимум 32; комната без единого подключённого сокета удаляется через 20 минут после последнего сообщения (`ROOM_IDLE_MS`). Открытый сокет держит комнату, даже если игрок молчит. Перезапуск сервера теряет комнаты из памяти, но забег лежит на диске (`RUNS_DIR`) и поднимается снова при `join`/`reconnect` по коду комнаты: сохранённый токен переживает перезапуск. Вместе с забегом сохраняется и `luck` хоста, иначе новый забег в поднятой комнате шёл бы с нулевой удачей.

Действия одной комнаты выполняются строго по одному через очередь на комнату: симуляция общая, и два параллельных хода перемешали бы состояние.

Возобновление требует токен: обычный `join` всегда создаёт нового героя, даже если имя совпадает с отключившимся — кода комнаты и имени недостаточно, чтобы перехватить сессию.

## Сервер → клиент

| Type | Смысл |
|---|---|
| `rooms` | Список комнат: `code`, `started`, `capacity`, `players` (`id`, `name`, `classId`, `host`, `connected`). Отправляется на `list` и подписанным сокетам при любом изменении комнат. |
| `runs` | Забеги с диска сервера: `code` и `players` (`name`, `classId`). Ответ на запрос `runs`. |
| `room-created` | Комната создана: `room`, `playerId`, `token` для переподключения, `players`. |
| `joined`, `host-reconnected` | Вход/возобновление: идентичность и игроки; `state` — для возобновлённого игрока, если доступен. |
| `players` | Обновлённый список игроков комнаты. |
| `host-disconnected` | Браузер хоста ушёл; забег продолжается на сервере. |
| `state` | Снимок: `state`, `turn`, `actor`, `log` (строки журнала с прошлого снимка), `effects` (вызовы анимаций с прошлого снимка), `screen`, `banked` (золото партии, только в финальном снимке). `state` несёт `game` и `mapState` каждый раз, а `map` и `world` — только когда они изменились. |
| `chat` | Сообщение от игрока. |
| `chat-error` | Сообщение отклонено лимитом. |
| `error` | Человекочитаемый `message` + стабильный `code`, если клиенту нужно реагировать (`bad-token`, `no-room`: сохранённая сессия мертва, её нужно забыть). |

`screen` — экран, который открыл герой из `actor`: `{ playerId, name, npcId? }`. `name` — панель из `RK.GameUI.SCREENS` (`js/game-ui.js`); экран `game` — переключение вида, клиент открывает его сам, поэтому в снимок он не едет.

В режиме мира (`CONFIG.ENABLE_WORLD`) снимок несёт ещё `state.world`: `current` (текущая локация) и `visited` с состоянием остальных локаций. Карта текущей локации едет полем `state.map`, поэтому её запись в `visited` исключена — запись пересобирается на клиенте из `state.map`. Переходы локаций происходят на сервере при шаге героя на клетку выхода; отдельного действия `travel` в протоколе нет.

## Снимок

Снимок уходит на каждый шаг, поэтому делится по частоте изменений:

| Часть | Что внутри | Когда меняется |
|---|---|---|
| `state.game` | Партия, враги (включая состояние фаз босса), предметы, NPC, задания, ход | на каждом шаге |
| `state.mapState` | то, что сделала игра: `blood`, `traps`, `doors`, `chests`, временные зоны фаз боссов, `explored` | на каждом шаге |
| `state.map` | геометрия локации: клетки, стены, комнаты, выходы, здания, декорации, факелы | только при новой локации |
| `state.world` | состояние остальных посещённых локаций | при переходе между локациями |

Поля карты, которые меняет игра, объявлены в `MAP_STATE_FIELDS` (`js/map-codec.js`): он же отрезает их от карты и собирает обратно в `restoreMap`, поэтому половины не расходятся. `js/combat-snapshot.js` только режет карту на части и собирает обратно.

### Сжатие

- Матрицы `tiles`, `floorTypes`, `regions`, `explored` едут в `state.map.matrices` как пары `[значение, длина]` на серию одинаковых клеток.
- `state.map.vis` не едет вовсе: он посчитан для того, кто ходил, а клиент пересчитывает обзор от своего героя.
- `wallTypes` едет как есть: он влияет на цвет стен, а сжатие RLE его раздувает.
- Матрица, которая не разворачивается ровно в `w × h`, отвергается как битая.

Сжатие живёт в `js/map-codec.js` (`encodeMatrices` / `decodeMatrices`), списки полей — там же. Новое поле матрицы достаточно добавить в `MATRIX_FIELDS`; снимок берёт список оттуда, а не повторяет своим.

### Доставка

Комната помнит сериализованную копию `map` и `world` и отправляет их только при изменении. Клиент (`js/network.js`) держит последнюю копию и подставляет её сам; первый снимок и сообщение о входе едут целиком. Снимок без `map` неполон, и клиент без своей копии его не примет. Рассылка сериализует сообщение один раз на комнату, а не на каждый сокет.

На карте 48×34 первый снимок локации весит около **30 KB**, шаг — около **9 KB** против ~27 KB на шаг без разделения частей.

`RK.Combat.applySnapshot()` (`js/combat-snapshot.js`) разворачивает матрицы, указывает `RK.GAME.player` на героя с локальным `id`, пересчитывает поле зрения и анимирует изменение на одну клетку. Снимок без `state.game` или `state.map` отвергается.

Шаг публикуется дважды: промежуточный снимок на середине анимации и итоговый после неё. Клиент, который читает состояние по снимкам, должен брать последний — иначе он увидит ход на полшага назад.

Сервер публикует по шагу, а не по действию: автопроход по клику — одно `playerAction` на много клеток. `RK.Combat.stepsDone()` считает завершённые анимации шагов; `createRun().act()` сообщает их через `onStep`, и `RoomManager.applyAction()` шлёт снимок на каждый. Если шагов не было — снимок один, после завершения.

### Эффекты боя

Сервер считает бой, но не рисует: `RK.Effects` в его движке только записывает вызовы. Вместе со снимком он шлёт список `effects` — `[имя метода, ...аргументы]`, — а клиент проигрывает их своим `RK.Effects` после применения снимка. Так доходят файрбол, молния, выстрелы, кольца и числа урона.

Список проигрываемых методов — `CONFIG.EFFECT_METHODS` (`js/config.js`): его читают и серверная заглушка, и клиент (`js/network.js`). Новая анимация вне списка молча исчезнет в сетевой игре, поэтому метод добавляется в конфиг один раз для обоих.

## Как добавить действие

Действие протокола живёт в четырёх местах, и правка нужна во всех:

1. Правило в `ACTION_RULES` (`server/room-manager.js`): функция проверяет `args.length` и границы. Пределы бери из `js/config.js` готовыми проверками (`isTileCoordinate`, `isSlot`, `isBackpackIndex`), а не своими числами: клиент и сервер читают один конфиг. Catch-all нет намеренно — иначе новое действие проходит молча.
2. Обработчик в `ACTION_HANDLERS` (`js/combat.js`, функция `actionHandlers()`): поведение на забеге. Старое имя от прошлых клиентов вешай через `aliasHandlers`, а не дублируй функцию.
3. Клиент шлёт `{ type: 'action', action, args }` (`js/network.js`), если действие идёт из интерфейса.
4. Покрытие в `tests/lan-server.test.js`: правило и обработчик проверяются вместе, включая отказ по пределам и неверным аргументам.

Кузнец принимает `craftEquipment` с аргументами `[slot, recipeId]`. Сервер ограничивает слот и `recipeId` списком `CONFIG.CRAFTING_RECIPE_IDS`; совместимость вещи, класс героя и наличие материалов проверяет игровой движок. Материалы и зачарованные характеристики входят в обычные поля предметов и рюкзака, поэтому отдельный формат снимка не нужен.

Секретные входы открываются по числу разных побеждённых боссов в `game.stats.bossKillsByName`; снимок уже несёт это состояние. Городской выход в Храм Солнца — исключение: он ведёт в локацию до выполнения условия, но пустынный вход и прямой переход остаются закрыты до двух разных боссов. Особый босс и его награда сохраняются обычными полями врага и предмета, поэтому повторное подключение не сбрасывает условие входа и не создаёт награду заново.

## Безопасность транспорта

Сервер рассчитан на доверенную LAN и не защищён от недоверенной сети:

- WebSocket-апгрейд отклоняет запросы, чей `Origin` не совпадает с хостом и схемой запроса, — это блокирует cross-site WebSocket hijacking со страницы в браузере хоста.
- HTTP-ответы несут ограничительные `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
- Соединения периодически пингуются; пропустившие раунд сокеты закрываются, а не держат слот комнаты.
- Токены переподключения сравниваются в постоянном времени; имена нормализуются и ограничиваются по длине до сохранения и рассылки.
- Ключи объектов от клиентов проверяются через `hasOwnProperty`, чтобы `size: 'constructor'` не протащил значение через `Object.prototype`.
- Файл забега читается как недоверенный ввод: `run-store` проверяет имя, размер, версию и форму игроков (см. [`architecture.md`](architecture.md), §4.3). Имя собирается только из кода комнаты, иначе `../../etc/passwd` стал бы путём за пределами каталога.
- Файл комнаты содержит токены переподключения её игроков: читающий каталог получает их вместе с забегом, поэтому каталог недоступен посторонним.

Сервер исполняет правила игры, что снимает прежнюю проблему «решает браузер хоста», но модифицированный клиент всё ещё может слать необычные действия в пределах allowlist.
