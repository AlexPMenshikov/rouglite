# LAN protocol

Сервер отдаёт клиент по HTTP и ретранслирует WebSocket-сообщения на `/ws`. Сообщения — JSON с полем `type`.

Сервер авторитетен в кооперативе: он загружает те же игровые скрипты, что и браузер (`ENGINE_SCRIPTS` из `scripts/script-list.js`) в контекст `node:vm`, выполняет валидированные действия игроков и рассылает снимок комнате после каждого хода. Одиночная игра полностью в браузере и сервер не касается.

Авторитет живёт в процессе сервера и не зависит от окон браузера.

## Client → server

| Type | Fields | Кто и что |
|---|---|---|
| `list` | — | Любой; отвечает списком комнат и, пока сокет не в комнате, подписывает его на обновления списка. |
| `create` | `name`, опц. `classId`, опц. `luck` | Новый; создаёт комнату и игрока-хоста. `luck` — удача мета-прогрессии хоста, влияет на находки золота партии. |
| `join` | `room`, `name`, опц. `classId` | Новый; входит новым героем. Продолжить героя можно только через `reconnect` с его токеном. |
| `reconnect` | `room`, `token`, `name` | Новый; возобновляет игрока по сохранённому токену. Токен — единственное удостоверение для возврата в сессию. |
| `selectClass` | `classId` | Любой игрок; класс запоминается до старта забега. После старта сменить нельзя — герой уже создан. |
| `start` | `options` (`size`, `style`, `classId`) | Только хост; начинает забег всей партии. Неизвестные `size`/`style` — к значениям по умолчанию, неизвестный `classId` — к классу игрока. |
| `kick` | `playerId` | Только хост; выгоняет **отключённого** игрока и освобождает слот. Подключённого так не выкинуть — он вернулся бы переподключением. |
| `action` | `action`, `args` | Имя — в allowlist сервера и проходит проверку аргументов, соединение — в лимите (20/с). Выполняется на общем забеге. |
| `chat` | `text` | Любой игрок; лимит 5 сообщений за 5 с. |

`classId` — один из `PLAYER_CLASSES` (`js/config.js`), иначе `paladin`. Старое имя `tank` не в списке, поэтому падает в `paladin` общим правилом неизвестного `classId`. Вместимость комнаты — 6 игроков. Комнаты в памяти, максимум 32; комната без единого подключённого сокета удаляется через 20 минут после последнего сообщения (`ROOM_IDLE_MS`, один срок и для подметалки по таймеру, и для счёта `MAX_ROOMS`). Перезапуск сервера теряет комнаты из памяти, но забег лежит на диске (`RUNS_DIR`) и поднимается снова при `join`/`reconnect` по коду комнаты: сохранённый токен переживает перезапуск. Вместе с забегом сохраняется и `luck` хоста, иначе новый забег в поднятой комнате шёл бы с нулевой удачей.

Действия одной комнаты выполняются строго по одному через очередь на комнату: симуляция общая, и два параллельных хода перемешали бы состояние.

Возобновление требует токен: обычный `join` всегда создаёт нового героя, даже если имя совпадает с отключившимся — кода комнаты и имени недостаточно, чтобы перехватить сессию.

## Server → client

| Type | Смысл |
|---|---|
| `rooms` | Список комнат: `code`, `started`, `capacity`, `players` (`id`, `name`, `classId`, `host`, `connected`). Отправляется на `list` и подписанным сокетам при любом изменении комнат. |
| `room-created` | Комната создана: `room`, `playerId`, `token` для переподключения, `players`. |
| `joined`, `host-reconnected` | Вход/возобновление: идентичность и игроки; `state` — для возобновлённого игрока, если доступен. |
| `players` | Обновлённый список игроков комнаты. |
| `host-disconnected` | Браузер хоста ушёл; забег продолжается на сервере. |
| `state` | Снимок: `state`, `turn`, `actor`, `log` (строки журнала с прошлого снимка), `effects` (вызовы анимаций с прошлого снимка), `screen`, `banked` (золото партии, только в финальном снимке). `state` несёт `game` и `mapState` каждый раз, а `map` и `world` — только когда они изменились. Один снимок на завершённый шаг хода и один на действие без шага (атака, навык, предмет). |
| `chat` | Сообщение от игрока. |
| `chat-error` | Сообщение отклонено лимитом. |
| `error` | Человекочитаемый `message` + стабильный `code`, если клиенту нужно реагировать (`bad-token`, `no-room`: сохранённая сессия мертва, её нужно забыть). |

`screen` — экран, который открыл герой из `actor`: `{ playerId, name, npcId? }`. `name` — `merchant`, `blacksmith` или `npc`; у `npc` есть `npcId` (вид NPC из `CONFIG.NPC_KINDS`), по которому клиент открывает экран разговора. Клиент показывает экран только тому, чей `playerId` совпал с его героем.

В режиме мира (`CONFIG.ENABLE_WORLD`) снимок несёт ещё `state.world`: `current` (текущая локация) и `visited` с состоянием остальных локаций. Карта текущей локации едет полем `state.map`, поэтому её запись в `visited` исключена — запись пересобирается на клиенте из `state.map`. Переходы локаций происходят на сервере при шаге героя на клетку выхода; отдельного действия `travel` в протоколе нет.

### Сжатие карты в снимке

Снимок уходит на каждый шаг, поэтому карта едет сжатой, а не открытыми массивами:

- Матрицы `tiles`, `floorTypes`, `regions`, `explored` хранятся в `state.map.matrices` как пары `[значение, длина]` на серию одинаковых клеток. `state.map.vis` не едет вовсе: он посчитан для того, кто ходил, а клиент пересчитывает обзор от своего героя.
- `RK.Combat.applySnapshot()` разворачивает матрицы в обычные строки и собирает пустую сетку `vis`. Матрица, которая не разворачивается в карту ровно `w × h`, отвергается как битая.
- `wallTypes` едет как есть: он влияет на цвет стен, а сжатие RLE его раздувает.

### Неизменная часть снимка

Карта локации не меняется, пока герой на той же локации, но снимок приходит на каждый шаг. Поэтому снимок разделён на две части по тому, кто их меняет:

| Часть | Что внутри | Когда меняется |
|---|---|---|
| `state.map` | геометрия локации: клетки, стены, комнаты, выходы, здания, декорации, факелы | только при новой локации |
| `state.mapState` | то, что сделала игра: `blood`, `traps`, `doors`, `chests`, `zones` | на каждом шаге |
| `state.world` | состояние остальных посещённых локаций | при переходе между локациями |
| `state.game` | партия, враги, предметы, NPC, задания, ход | на каждом шаге |

Список игровых полей — `MAP_STATE_FIELDS` в `js/combat-snapshot.js`: он же отрезает их от карты и собирает обратно в `restoreMap`, поэтому половины не расходятся.

Комната помнит сериализованную копию `map` и `world` и отправляет их только когда они изменились. Клиент (`js/network.js`) держит последнюю копию и подставляет её сам; первый снимок и сообщение о входе едут целиком. На карте 48×34 это даёт около **30 KB в первом снимке локации и около 9 KB на шаг** против ~27 KB на шаг раньше.

Подстановка копии — не украшение, а часть контракта: снимок без `map` неполон, и клиент без своей копии его не примет. Рассылка комнаты сериализует сообщение один раз на комнату, а не на каждый сокет.

Сжатый снимок весит около 9 KB на шаг против 27 KB на ту же локацию без разделения частей.

Клиенты применяют `state` для всех: `RK.Combat.applySnapshot()` (`js/combat.js`) указывает `RK.GAME.player` на героя с локальным `id`, а `js/render.js` пересчитывает поле зрения от этого героя. Изменение на одну клетку любого участника анимируется локально — герой не телепортируется.

Шаг публикуется дважды: промежуточный снимок на середине анимации и итоговый после неё. Клиент, который читает состояние по снимкам, должен брать последний — иначе он увидит ход на полшага назад.

Сервер публикует по шагу, а не по действию: автопроход по клику — одно `playerAction` на много клеток. `RK.Combat.stepsDone()` считает завершённые анимации шагов; `createRun().act()` сообщает их через `onStep`, и `RoomManager.applyAction()` шлёт снимок на каждый. Если шагов не было — снимок один, после завершения, дублей клиенты не видят.

### Эффекты боя

Сервер считает бой, но не рисует: `RK.Effects` в его движке только записывает вызовы.
Вместе со снимком он шлёт список `effects` — `[имя метода, ...аргументы]`, — а клиент
проигрывает их своим `RK.Effects` после применения снимка. Так доходят файрбол,
молния, выстрелы, кольца и числа урона: без них сетевая игра выглядела бы как
телепорт результатов.

Список проигрываемых методов — `CONFIG.EFFECT_METHODS` (`js/config.js`): его читают и
серверная заглушка, и клиент (`js/network.js`). Новая анимация вне списка молча
исчезнет в сетевой игре, поэтому метод добавляется в конфиг один раз для обоих.

## Transport security

Сервер рассчитан на доверенную LAN и не защищён от недоверенной сети:

- WebSocket-апгрейд отклоняет запросы, чей `Origin` не совпадает с хостом и схемой запроса, — это блокирует cross-site WebSocket hijacking со страницы в браузере хоста.
- HTTP-ответы несут ограничительные `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
- Соединения периодически пингуются; пропустившие раунд сокеты закрываются, а не держат слот комнаты.
- Токены переподключения сравниваются в постоянном времени; имена нормализуются и ограничиваются по длине до сохранения и рассылки.
- Ключи объектов от клиентов проверяются через `hasOwnProperty`, чтобы `size: 'constructor'` не протащил значение через `Object.prototype`.
- Имя файла сохранённого забега собирается только из букв и цифр кода комнаты: код приходит от клиента, и без проверки `../../etc/passwd` стал бы путём за пределами каталога.
- Сохранённый забег читается с теми же проверками, что и сообщение из сокета, и отвергается при превышении размера файла.

Состояние комнат живёт в памяти процесса, а забег дублируется на диск (`RUNS_DIR`, по умолчанию `data/runs/`), чтобы пережить перезапуск сервера. Файл комнаты содержит токены переподключения её игроков: читающий каталог получает их вместе с забегом, поэтому каталог недоступен посторонним. Сервер исполняет правила игры, что снимает прежнюю проблему «решает браузер хоста», но модифицированный клиент всё ещё может слать необычные действия в пределах allowlist.

Комната без подключённых игроков удаляется через 20 минут после последнего сообщения; забег перед удалением ложится на диск. Открытый сокет держит комнату, даже если игрок молчит.

## Snapshot shape

Сервер считает снимки своей сериализацией и требует только `state.game` и `state.map`. Клиент создаёт и применяет их через `RK.Combat.createSnapshot()` и `RK.Combat.applySnapshot()` (`js/combat-snapshot.js`); внутренняя схема следует сериализованным состояниям игры и карты, включая идентичность игроков. Меняйте производство снимков (`server/game-engine.js`) и восстановление (`js/combat-snapshot.js`) вместе.

Сжатие матриц живёт в `js/map.js` (`encodeMatrices` / `decodeMatrices`), список полей — там же, и он отдаётся как `RK.MapGen.MATRIX_FIELDS`: снимок берёт его оттуда, а не повторяет своим списком. Новое поле матрицы достаточно добавить в `MATRIX_FIELDS`.

Поля карты, которые меняет игра, объявлены в `MAP_STATE_FIELDS` (`js/combat-snapshot.js`) — они едут отдельной частью `mapState` и не делают карту «изменившейся».

## Adding an action

Действие протокола живёт в трёх местах, и правка нужна во всех:

1. Правило в `ACTION_RULES` (`server/room-manager.js`): функция проверяет `args.length` и границы. Пределы бери из `js/config.js` готовыми проверками (`isTileCoordinate`, `isSlot`, `isBackpackIndex`), а не своими числами: клиент и сервер читают один конфиг. Catch-all нет намеренно — иначе новое действие проходит молча.
2. Обработчик в `ACTION_HANDLERS` (`js/combat.js`, функция `actionHandlers()`): поведение на забеге. Старое имя от прошлых клиентов вешай через `aliasHandlers`, а не дублируй функцию.
3. Клиент шлёт `{ type: 'action', action, args }` (`js/network.js`), если действие идёт из интерфейса.
4. Покрытие в `tests/lan-server.test.js`: правило и обработчик проверяются вместе, включая отказ по пределам и неверным аргументам.
