# LAN protocol

Сервер отдаёт клиент по HTTP и ретранслирует WebSocket-сообщения на `/ws`. Сообщения — JSON с полем `type`.

Сервер авторитетен в кооперативе: он загружает те же игровые скрипты, что и браузер (`config`, `rng`, `map`, `world`, `entities`, `items`, `fov`, `narrator`, `classes`, `npc`, `meta`, `combat`) в контекст `node:vm`, выполняет валидированные действия игроков и рассылает снимок комнате после каждого хода. Одиночная игра полностью в браузере и сервер не касается.

Авторитет на сервере, потому что прежняя схема «ведёт хост» привязывала общий такт к `requestAnimationFrame` хоста: свёрнутое окно хоста не даёт кадров, анимация шага не завершается, и удалённые игроки не могут ходить. Процесс сервера не зависит от окон браузера.

## Client → server

| Type | Fields | Кто и что |
|---|---|---|
| `list` | — | Любой; отвечает списком комнат и, пока сокет не в комнате, подписывает его на обновления списка. |
| `create` | `name`, опц. `classId`, опц. `luck` | Новый; создаёт комнату и игрока-хоста. `luck` — удача мета-прогрессии хоста, влияет на находки золота партии. |
| `join` | `room`, `name`, опц. `classId` | Новый; входит новым героем. Продолжить героя можно только через `reconnect` с его токеном. |
| `reconnect` | `room`, `token`, `name` | Новый; возобновляет игрока по сохранённому токену. Токен — единственное удостоверение для возврата в сессию. |
| `start` | `options` (`size`, `style`) | Только хост; начинает забег всей партии. Неизвестные `size`/`style` — к значениям по умолчанию. |
| `action` | `action`, `args` | Имя — в allowlist сервера и проходит проверку аргументов, соединение — в лимите (8/с). Выполняется на общем забеге. |
| `chat` | `text` | Любой игрок; лимит 5 сообщений за 5 с. |

`classId` — один из `PLAYER_CLASSES` (`js/config.js`), иначе `tank`. Вместимость комнаты — 4 игрока. Комнаты в памяти, максимум 32, неактивные отключившиеся удаляются через 2 часа. Перезапуск сервера сбрасывает комнаты и забеги.

Действия одной комнаты выполняются строго по одному через очередь на комнату: симуляция общая, и два параллельных хода перемешали бы состояние.

Возобновление требует токен: обычный `join` всегда создаёт нового героя, даже если имя совпадает с отключившимся — кода комнаты и имени недостаточно, чтобы перехватить сессию.

## Server → client

| Type | Смысл |
|---|---|
| `rooms` | Список комнат: `code`, `started`, `capacity`, `players` (`id`, `name`, `classId`, `host`, `connected`). Отправляется на `list` и подписанным сокетам при любом изменении комнат. |
| `room-created` | Комната создана: `room`, `playerId`, `token` для переподключения, `players`. |
| `joined`, `host-reconnected` | Вход/возобновление: идентичность и игроки; `state` — для возобновлённого игрока, если доступен. |
| `players` | Обновлённый список игроков комнаты. |
| `host-disconnected` | Браузер хоста ушёл; забег продолжается на сервере. |
| `state` | Снимок: `state`, `turn`, `actor`, `log` (строки журнала с прошлого снимка), `screen`, `banked` (золото партии, только в финальном снимке). Один снимок на завершённый шаг хода и один на действие без шага (атака, навык, предмет). |

`screen` — экран, который открыл герой из `actor`: `{ playerId, name, npcId? }`. `name` — `merchant`, `blacksmith` или `npc`; у `npc` есть `npcId` (вид NPC из `CONFIG.NPC_KINDS`), по которому клиент открывает экран разговора. Клиент показывает экран только тому, чей `playerId` совпал с его героем.

В режиме мира (`CONFIG.ENABLE_WORLD`) снимок несёт ещё `state.world`: `current` (текущая локация) и `visited` с состоянием остальных локаций. Карта текущей локации едет полем `state.map`, поэтому её запись в `visited` исключена — запись пересобирается на клиенте из `state.map`. Переходы локаций происходят на сервере при шаге героя на клетку выхода; отдельного действия `travel` в протоколе нет.

### Сжатие карты в снимке

Снимок уходит на каждый шаг, поэтому карта едет сжатой, а не открытыми массивами:

- Матрицы `tiles`, `floorTypes`, `regions`, `explored` хранятся в `state.map.matrices` как пары `[значение, длина]` на серию одинаковых клеток. `state.map.vis` не едет вовсе: он посчитан для того, кто ходил, а клиент пересчитывает обзор от своего героя.
- `RK.Combat.applySnapshot()` разворачивает матрицы в обычные строки и собирает пустую сетку `vis`. Матрица, которая не разворачивается в карту ровно `w × h`, отвергается как битая.
- `wallTypes` едет как есть: он влияет на цвет стен, а сжатие RLE его раздувает.

Сжатый снимок весит около 18 KB против 42 KB на одну локацию.
| `chat` | Сообщение от игрока. |
| `chat-error` | Сообщение отклонено лимитом. |
| `error` | Человекочитаемый `message` + стабильный `code`, если клиенту нужно реагировать (`bad-token`, `no-room`: сохранённая сессия мертва, её нужно забыть). |

Клиенты применяют `state` для всех: `RK.Combat.applySnapshot()` (`js/combat.js`) указывает `RK.GAME.player` на героя с локальным `id`, а `js/render.js` пересчитывает поле зрения от этого героя. Изменение на одну клетку любого участника анимируется локально — герой не телепортируется.

Шаг публикуется дважды: промежуточный снимок на середине анимации и итоговый после неё. Клиент, который читает состояние по снимкам, должен брать последний — иначе он увидит ход на полшага назад.

Сервер публикует по шагу, а не по действию: автопроход по клику — одно `playerAction` на много клеток. `RK.Combat.stepsDone()` считает завершённые анимации шагов; `createRun().act()` сообщает их через `onStep`, и `RoomManager.applyAction()` шлёт снимок на каждый. Если шагов не было — снимок один, после завершения, дублей клиенты не видят.

## Transport security

Сервер рассчитан на доверенную LAN и не защищён от недоверенной сети:

- WebSocket-апгрейд отклоняет запросы, чей `Origin` не совпадает с хостом и схемой запроса, — это блокирует cross-site WebSocket hijacking со страницы в браузере хоста.
- HTTP-ответы несут ограничительные `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
- Соединения периодически пингуются; пропустившие раунд сокеты закрываются, а не держат слот комнаты.
- Токены переподключения сравниваются в постоянном времени; имена нормализуются и ограничиваются по длине до сохранения и рассылки.
- Ключи объектов от клиентов проверяются через `hasOwnProperty`, чтобы `size: 'constructor'` не протащил значение через `Object.prototype`.
- Имя файла сохранённого забега собирается только из букв и цифр кода комнаты: код приходит от клиента, и без проверки `../../etc/passwd` стал бы путём за пределами каталога.
- Сохранённый забег читается с теми же проверками, что и сообщение из сокета, и отвергается при превышении размера файла.

Состояние комнат живёт в памяти процесса, а забег дублируется на диск (`RUNS_DIR`, по умолчанию `data/runs/`), чтобы пережить перезапуск сервера. Файл комнаты содержит токены переподключения её игроков: читающий каталог получает их вместе с забегом, поэтому каталог недоступен посторонним. Сервер исполняет правила игры, что снимает прежнюю проблему «решает браузер хоста», но модифицированный клиент всё ещё может слать необычные действия в пределах allowlist.

Комната без подключённых игроков удаляется через 20 минут после последнего сообщения; забег перед удалением ложится на диск. Открытый сокет держит комнату, даже если игрок молчит.

## Snapshot shape

Сервер считает снимки своей сериализацией и требует только `state.game` и `state.map`. Клиент создаёт и применяет их через `RK.Combat.createSnapshot()` и `RK.Combat.applySnapshot()` (`js/combat.js`); внутренняя схема следует сериализованным состояниям игры и карты, включая идентичность игроков. Меняйте производство снимков (`server/game-engine.js`) и восстановление (`js/combat.js`) вместе.

Сжатие матриц живёт в `js/map.js` (`encodeMatrices` / `decodeMatrices`), список полей — там же. Список в `js/combat.js` повторяет его: снимок убирает поля из карты, а `applySnapshot` разворачивает их обратно. Новое поле матрицы требует правки обоих списков, иначе оно уедет на клиент сжатым или потеряется.

## Adding an action

1. Действие — в `js/combat.js`: в `ACTION_HANDLERS`, если оно может прийти от игрока, и проверьте локальную работу.
2. Имя и строгая валидация аргументов — в `ACTION_RULES` (`server/room-manager.js`). Каждому действию нужное явное правило: у таблицы нет прототипа и нет catch-all, отсутствующая запись отклоняется, а не принимается молча. Границы аргументов, зеркалящие игру (размеры карты, слоты экипировки, виды NPC), — из `js/config.js`, который сервер подключает напрямую.
3. Покройте валидное выполнение, невалидные аргументы и лимиты в `tests/lan-server.test.js`.
